## 2026-10-04 · biz4sale — сайт прод, тестовые данные удалять сразу
Пользователь: «этот сайт это прод, все данные которые ты делаешь должен сразу удалить».
**Правило:** на biz4sale.co.il создавать данные только когда без этого не проверить; помечать «QA-TEST»; записывать в context.md → «Тестовые данные для чистки»; удалять сразу после проверки (кнопку удаления — по подтверждению пользователя); реальные объявления/пользователей не трогать.

## L-20261029-1 · Технические ошибки без видимого эффекта — не заводить
- Правило: ошибка видна только в консоли или в ответе сервера (например, 403 на служебную запись), а для пользователя всё работает и клиент не жалуется → не предлагать как баг к заведению. Максимум — строка в «находках» с пометкой «тех., без эффекта».
- Почему: «удалил, так как работает сейчас нормально, если оно работает и клиент не жалуется» (про #b81c35, business_approval 403 RLS).
- Пример: POST business_approval 403 на «שלח» — объявление уходит на одобрение нормально.
- Источник: сообщение пользователя, 2026-10-29
- Область: проект
- Статус: действует

## L-20261110-1 · Баг «на входе X» — проверять только сам симптом, без расширенного регресса
- Правило: для бага с узким симптомом (напр. «белый экран при входе») проверять только этот симптом на нужном устройстве (вход → нет симптома + 1 замер). Не проверять все вкладки/пагинацию/колонки/связанные тикеты вширь, если пользователь не попросил.
- Почему: «просто проверить если при заходе нету белого экрана, не вижу смысла растягивать тест этого на 20 минут».
- Пример: #6dd27f — мобильный /admin: вход через меню → «ניהול - פאנל מנהל», нет белого экрана, scrollWidth = ширине экрана.
- Источник: сообщение пользователя, 2026-11-10
- Область: проект
- Противоречит: общий урок L-20261003-4 («по всему чек-листу») и qa-ticket-analysis (регресс связанных тикетов) — для узких багов этот урок важнее.
- Статус: действует
