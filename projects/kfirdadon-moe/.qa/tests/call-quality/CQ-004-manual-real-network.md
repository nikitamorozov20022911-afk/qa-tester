# CQ-004 (вручную): реальное ухудшение сети и серверный статус записи при RTT ~450 мс
- Фича/экран: звонок S-16, отчёт S-19 «מצב טכני», /admin/support
- Тикеты: #51da2a (b28a22ed6a85bb764151da2a)
- Роль/аккаунт: business + кандидат (гость); реальный телефон в мобильной сети
- Устройство: iPhone / Android по кабелю (qa-device) или Mac с Network Link Conditioner (системная настройка — только с разрешения пользователя)
- Тип: ручной; @call — тратит OpenAI
## Шаги
1. Звонок из реальной мобильной сети (RTT ≥ 400 мс, если получится) — смотреть плашку весь звонок, затем quality_status в отчёте.
2. (Опционально) ухудшить сеть на уровне ОС (потери > 20 %) — плашка появляется, звонок идёт, после — quality_status «degraded».
## Ожидаемо
- При обычной сети, в т.ч. RTT ~450 мс: плашки нет постоянно, recording.quality_status = sufficient (AC тикета).
- При реальных потерях > 20 %: плашка, звонок продолжается (F-32 AC).
## Почему вручную
- В recording_quality.latency_ms клиент отправляет максимальный RTT (не delay_ms); как сервер ставит degraded при latency_ms ≈ 450 — не проверено (14.10 реальный RTT был ~155 мс). Автотест CQ-001 может подменить RTT (QA_CALL_FORCE_RTT_MS=450), но это подмена на клиенте, не реальная сеть.
- Реальная потеря UDP-пакетов без системных настроек не воспроизводится; CQ-003 проверяет только клиентскую логику.
- Открытый вопрос владельцу: «השהיה מעל 400» — RTT или delay_ms (RTT/2 + буфер)?
