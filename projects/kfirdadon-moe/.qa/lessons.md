## L-20261012-2 · Supabase-сессии: один файл входа — один агент, после работы сохранять обратно
- Правило: refresh-токен Supabase одноразовый. Любой запуск браузера с файлом .qa/auth/<id>.json, который обновил токен и не сохранил состояние обратно, убивает этот файл для всех. Поэтому: (1) каждому параллельному агенту — свой слот входа (<id>.json, <id>-2.json, <id>-3.json; создаёт npm run qa-login); (2) в конце работы агент делает state-save в СВОЙ слот; (3) мои проверочные скрипты тоже сохраняют storageState обратно в тот же файл.
- Почему: 2026-10-12 мой стартовый скрипт проверки сессий и параллельные агенты израсходовали refresh-токены admin/business/user → «refresh_token_already_used», все перепроверки заблокированы, понадобился вход пользователя.
- Источник: ошибка агента, 2026-10-12 · Область: проект (и общий для Supabase-сайтов) · Статус: действует

## L-20261013-1 · Сводку «прошёл» показывать только после перепроверки КАЖДОГО тикета из списка
- Изменено 2026-10-14 (решение пользователя, плагин 0.9.10): bug-verifier перепроверяет только провалы (❌) и находки, идущие в реджект; пункты ✅ с первого прогона не перепроверяются. Вердикт показывать по каждому тикету сразу, как он готов.
- Правило (было): перед итоговой сводкой сверить по журналу, у каких «прошёл» нет независимой перепроверки bug-verifier и у каких есть непроверенные пункты (пароль/звонок) — их в «прошёл» не включать, а писать «ждёт перепроверки» / «частично». То же для реджектов: в сводке только перепроверенные.
- Почему: пользователь спросил «вердикты ты дал после перепроверок по нашему уроку?» — в сводке 13.10 7 «прошёл» и 2 реджекта были без перепроверки, 3 «прошёл» — с непроверенным пунктом (повтор L-20261004-5).
- Источник: вопрос пользователя, 2026-10-13 · Область: общий · Статус: действует


## L-20261013-2 · Вердикт — только при 100% уверенности (ПОВТОРНАЯ ОШИБКА, раздражает пользователя)
- Правило: вердикт («прошёл» ИЛИ «реджект») показывать ТОЛЬКО когда уверенность 100%: каждый пункт тикета (AC, דרישות, пункты прошлых реджектов, документация/флоу, Figma) проверен фактически (провалы — ещё и независимо перепроверены bug-verifier; ✅ с первого прогона не перепроверяются — изменено 14.10, плагин 0.9.10), и нет ни одного пункта «не проверено / частично / подмена / только UI / нужен пароль / вопрос». Если хоть что-то не так — это НЕ вердикт, а «не готово» с точным списком: что осталось, почему, что нужно (действие агента / «да» пользователя / пароль / решение владельца). Сначала довести проверку до 100% всеми доступными способами, и только потом показывать вердикт. В сводке не должно быть «почти уверен».
- Почему: «зачем ты даешь вердикты если ты не уверен в них 100%? это уже начинает бесить. тесть так что бы когда ты даешь вердикт то что бы ты был уверен на 100%».
- Пример: kfir-dadon 13.10 — в «прошли» было 21 тикет, из них 100% — только 6.
- Связь: L-20261003-4, L-20261004-5, L-20261008-2, L-20261013-1 (то же правило, нарушено снова).
- Источник: сообщение пользователя, 2026-10-13 · Область: общий · Статус: действует · КАНДИДАТ В ПЛАГИН (/qa-improve): qa-verdict — ворота «100% или не готово»

## L-20261014-1 · Звонки/симуляции — один прогон, без повторного звонка для перепроверки
- Правило: в kfir-dadon каждую проверку, требующую голосового звонка (симуляции), делать ОДИН раз. Независимая перепроверка bug-verifier для таких пунктов — по записанным доказательствам (скриншоты, отчёт, API-ответы, запись звонка), без второго звонка. Вердикт по таким тикетам давать по одному прогону.
- Почему: «тесты симуляциям делай по 1 разу. если делать по 2 то будут быстро заканчиваться токены» (кредиты OpenAI закончились 14.10).

## L-20261014-6 · Реджект бага на доске заменяет «פרטי באג» — текст реджекта должен нести суть бага
- Правило: у тикетов типа «באג» доска mifrat показывает первый реджект в блоке «פרטי באג» (מה קיים / מה רצוי) вместо исходного описания. Поэтому в реджекте бага «מה קיים» всегда начинать с сути исходной проблемы тикета (его «מצב נוכחי»), а не только с того, почему QA не может проверить; «מה צריך לקרות» — с AC тикета; заполнять «שלבים לשחזור» и URL. Иначе программист с карточки не поймёт контекст.
- Почему: пользователь 14.10 — «программист не сможет понять контекста так как нету самого главного тикета» (14 реджектов «נדרשות ראיות» с пустыми шагами).
- Источник: сообщение пользователя, 2026-10-14 · Область: проект · Статус: действует

## L-20261021-3 — звук продавца в звонках только через fake-файл
Подмена getUserMedia через WebAudio (MediaStreamAudioDestinationNode) в headless Chrome даёт 12–16 аудиопакетов/с вместо 50: AI-клиент не находит конец реплики и молчит, транскрипт получает speaker=null, отчёт — «המועמד כמעט לא דיבר». Так испорчены звонки B1 (cecbbb93) и 0e9f9a (bc0fc9a2) 21.10. Подавать речь только флагами --use-fake-device-for-media-stream --use-file-for-fake-audio-capture=<wav> (паузы внутри WAV). Перед выводом «клиент молчит — баг сайта» проверить outbound packets/s (≈50).

## L-20261021-4 — не спрашивать то, что уже решено проверкой
21.10 спросил пользователя об «утверждении макетов» для 13 дизайн-задач, хотя все кадры прошли сверку с требованиями; вопрос был формальный (AC «ווירפריים מאושר») и только запутал. Дизайн-задачи: если кадры соответствуют тикету — сразу «прошёл». Вопрос задавать только когда от ответа меняется вердикт и это нельзя решить по Figma/требованиям.

## L-20261022-1 — Вердикт «проходит» только при всех проверенных пунктах
Что случилось: по #ebdb2f написал «можно проводить», хотя AC2 (язык), треб. 5 (чужой бизнес) и контакт в письме (AC1) не были проверены. Пользователь: «тогда зачем вердикт присылаешь?».
Правило: «можно проводить» — только когда КАЖДЫЙ AC/דרישה ✅. Есть хоть один ⚠️/не проверено → статус «не готово: <что осталось>», без слова «проводить».

## L-20261104-1 — Возврат после реджекта: сверять ВСЕ AC тикета, а не только пункты реджекта
Что случилось: #d9996c назвал «прошёл» по пунктам последнего реджекта + регрессу карточек, но AC «пустое состояние нового бизнеса» и «ошибка загрузки с обновлением» после двух переделок дашборда не перепроверялись. Пользователь: «по требованиям все прошло да?».
Правило: у вернувшегося тикета карта требований = все AC/דרישות тикета + пункты всех реджектов; пункт, который код мог задеть после прошлой проверки, — перепроверить; остальное — явно «проверено ранее <дата>». Пока хоть один AC не проверен после изменений — «не готово», без слова «прошёл».
Источник: сообщение пользователя, 2026-11-04 · Область: общий · Статус: действует

## L-20261117-1 — Общий блокер (внешний сервис/кредиты): реджект ОДНОГО тикета, остальные — «לא ניתן לשחזר» со ссылкой на него

## L-20261117-2 — «Прошёл» только после сверки с картой брифа: каждый ⚠/«не сверено» в карте закрыт (ПОВТОР L-20261013-2, L-20261104-1)
Что случилось: дал «прошёл» по #d65b5b (не проверил отчёт business после переноса подписей в общий файл) и #ece93f (в карте брифа R13 ⚠ «условие сценария не сверено», R11 и вид business не проверены). Пользователь: «точно прошли?».
Правило: перед вердиктом открыть карту требований в .qa/research/<id>.md и пройти КАЖДУЮ строку: ✅ сегодня / ✅ ранее и код не мог задеть / иначе — «не готово». Строки с ⚠ или «не сверено» из прошлых сессий не наследуются как ✅. Если агент проверил только часть ролей — роли, которые изменение могло задеть, остаются в «не готово».
