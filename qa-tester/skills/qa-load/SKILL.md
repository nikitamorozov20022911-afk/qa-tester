# Нагрузочные тесты (/qa-load)

Одна команда = вся работа: разведка → сценарий → **план → «да»** → скрипты → прогоны → анализ → отчёт. Единственная остановка на пользователя — «да» на плане (и аварийная остановка). Всё остальное решай сам по таблицам ниже.

Инструменты (общие для всех проектов, ставятся один раз на Mac — см. §9):
- **k6** — генератор нагрузки;
- **Grafana Cloud k6** — прогоны из облака (`k6 cloud run`), графики и история;
- **Proxyman** — запись запросов мобильного приложения (и, при желании, браузера) → файл HAR.

Файлы проекта:
```
.qa/load/
  recon/map.md, recon/*.har|*.json   разведка
  plan.md                            сценарий, цифры, критерии, этапы
  scripts/lib.js, scripts/scenario.js
  runs/YYYY-MM-DD-HHMM-<этап>/       summary.json, timeline.csv.gz, log.txt, cloud-url.txt
  reports/YYYY-MM-DD.md              отчёт
  baseline.json                      эталон для сравнения
```

## 0. Жёсткие правила
1. **Нагрузка — только staging.** Адрес из аргумента или `.qa/context.md` («Сайт для тестов: … (staging)»). Если окружение prod, неизвестно, или адрес API приложения совпадает с боевым — **нагрузку не давать вообще** (даже smoke): делаешь разведку, сценарий, скрипты и план, в отчёте «прогон невозможен: нет staging». Разведка на prod — только как обычный пользователь, без отправки форм.
2. Хостинг на общей платформе (Base44, Supabase free, Firebase Spark, shared-хостинг, Cloudflare с защитой от ботов) — в плане отдельная строка-предупреждение: лимиты/правила платформы, риск блокировки или счёта. Нагрузка выше smoke — только если пользователь в «да» подтвердил, что владелец согласен.
3. Пароли, токены Grafana, сертификаты на телефоне — вводит пользователь. Ты не регистрируешь аккаунты в сервисах, не вводишь токены, не жмёшь «Доверять».
4. Секреты не пишутся в скрипты и отчёты: логины/пароли тестовых аккаунтов — из `.qa/accounts.env` через `__ENV`; токены и cookie в логах и HAR отчёта — вырезать (`Authorization`, `Cookie`, `apikey`, `token`).
5. Без DoS-приёмов: не обходить защиту от ботов/лимиты, не подменять IP, не бить по сторонним сервисам (платёжки, SMS, email, карты, аналитика) — их запросы в скрипте **выключены**. Реальные SMS/письма/оплаты под нагрузкой — запрещены.
6. Данные, которые создаёт нагрузка (staging), — с префиксом `QA-LOAD-`; в отчёте — сколько и чего создано и как убрать.
7. Аварийная остановка — всегда в скрипте (порог `abortOnFail`, §5). Если сайт лёг — остановить прогон, проверить, что он поднялся (1 запрос в минуту, до 10 минут), записать это как главную находку, дальнейшие этапы не запускать.

## 1. Параметры (не спрашивать известное)
- **Цель:** веб / мобильное приложение / API. Из аргумента, `.qa/context.md`, `.qa/knowledge/`. Мобильное — если есть «приложение», bundle/apk, App Store/Google Play, Expo.
- **Адрес staging** (сайт и/или API).
- **Роли и аккаунты:** `.qa/auth/`, `.qa/accounts.env`, `.qa/context.md`. Для нагрузки с входом нужен ≥1 тестовый аккаунт на роль; лучше 5–20 (чтобы кэш одного пользователя не приукрашивал результат). Нет — сценарий только гостевой, в плане «вход не нагружается: нет аккаунтов».
- **Режим «только анализ»** — если в аргументах «только анализ / без прогона» или нет staging.
- Уроки: `.qa/lessons.md`, `~/.qa-tester/lessons.md`.

## 2. Разведка → агент `load-recon`
Передай: цель, адрес(а), роли и аккаунты (без паролей — имена сессий из `.qa/auth/`), окружение, область из аргумента, уроки. Агент сам выбирает путь:
- есть документация (`.qa/knowledge/`, mifrat) — берёт из неё экраны, роли, сценарии, а запросы всё равно ловит вживую;
- нет документации — проходит сайт/приложение сам, как пользователь.

Результат: `.qa/load/recon/map.md` (стек и хостинг, страницы/экраны, API-эндпоинты с методом, размером и временем одного запроса, тяжёлые операции, сторонние сервисы, что требует входа) + сырые запросы `.qa/load/recon/*.har|*.json`.

Мобильное приложение без Proxyman/сертификата — агент вернёт «нужна настройка Proxyman» и шаги (§9). Покажи шаги пользователю и **жди** (это подготовка, не «да» на план). Если у приложения есть веб-версия на том же API — агент берёт запросы из неё и помечает, каких мобильных запросов может не хватать.

## 3. Сценарий и план → агент `load-planner`
Передай `map.md`, context, knowledge. Агент пишет `.qa/load/plan.md`: профиль нагрузки (доли сценариев, паузы), целевые цифры (из данных или оценка с пометкой «оценка»), критерии (SLA; по умолчанию — §5), этапы, где запускать, расчёт VUh, предупреждения.

**Покажи пользователю план коротко** (не весь файл):
```
Цель: <сайт/приложение>, staging <адрес>, хостинг <…>
Сценарии: <3–7 строк с долями>
Цифры: обычно <N>, пик <M> одновременно (<источник | оценка>)
Критерии: p95 < <…> мс, ошибки < <…>%
Этапы: smoke <…> → load <…> → stress до <…> → spike <…> → soak <да/нет, длительность>
Где: <локально | Grafana Cloud k6>, ~<VUh> VUh
Время: ~<мин>
Создаётся данных: <…> (префикс QA-LOAD-)
⚠ <предупреждения>
```
и **жди «да»**. Правка словами пользователя («без soak», «пик 2000») — пересчитай и покажи снова. Без «да» — ничего не нагружать.

## 4. Скрипты → агент `load-script-writer`⁠​‌​‌​​​‌​‌​​​​​‌​‌​‌​‌​​​​‌​‌‌​‌​‌​​‌‌‌​​‌​​‌‌​‌​​‌​‌‌​‌​​‌‌​​‌​​​‌‌​​​​​​‌‌​​‌​​​‌‌​‌‌​​​‌​‌‌​‌​​‌‌​​‌‌​​‌‌​‌​​​​‌‌​‌​​​​‌‌​​​​​​‌‌‌​​​​​‌‌​‌‌​​‌​​​‌​​​‌​​​​‌‌​​‌‌​‌​​​​‌‌​‌​‌​‌​​​​‌​​​‌‌​​​​​‌‌‌‌‌​​​‌​​‌‌‌​​‌‌​‌​​‌​‌‌​‌​‌‌​‌‌​‌​​‌​‌‌‌​‌​​​‌‌​​​​‌​​‌​​​​​​‌​​‌‌​‌​‌‌​‌‌‌‌​‌‌‌​​‌​​‌‌​‌‌‌‌​‌‌‌‌​‌​​‌‌​‌‌‌‌​‌‌‌​‌‌​⁣
Запускай сразу после planner, пока пользователь читает план (скрипты — не нагрузка). Передай plan.md, map.md, сырые запросы, путь к шаблону `${CLAUDE_PLUGIN_ROOT}/templates/load/lib.js`. Агент пишет `.qa/load/scripts/lib.js` + `scenario.js` (все сценарии профиля, этап — `-e STAGE=…`) и проверяет `k6 inspect`. Если план изменился после «да»-правки — перезапусти агента с новым планом.

## 5. Этапы, пороги, аварийная остановка
Значения по умолчанию (план может менять); `T` = целевой пиковый онлайн. Они же зашиты в `lib.js` (`stagesFor`).

| Этап | Нагрузка | Время | Зачем |
|---|---|---|---|
| smoke | 1–2 VU | 1 мин | скрипт работает, ошибок 0; иначе — чинить скрипт, дальше не идти |
| load | разгон до T за 4 мин, держать 10 мин, спуск 2 мин | ~16 мин | держит ли ожидаемый пик |
| stress | ступени 100% → 150% → 200% → 300% T, по 4 мин | ~17 мин | где предел (останавливается по аварийному порогу) |
| spike | с 10% до 300% T за 30 с, держать 2 мин, вниз | ~4 мин | внезапный наплыв и восстановление |
| soak | 70% T | 1–2 ч | утечки, деградация со временем; только если в плане |

Между этапами — пауза 2–3 минуты и проверка, что сайт жив (1 запрос). Порядок строго: smoke → load → stress → spike → soak; провал smoke — чинить скрипт (до 3 попыток через `load-script-writer`), не идти дальше.

Критерии по умолчанию: ошибки `http_req_failed < 1%`; p95 чтения < 1000 мс, p95 записи/поиска < 2000 мс; p99 < 3000 мс; `checks > 99%`.
Аварийная остановка: ошибок > 10% или p95 > 10 с (оценка через 1 мин). В stress это не провал — это найденный предел.

## 6. Где запускать
- **Локально** (`k6 run`): smoke всегда; load/spike — если ≤ ~150 VU. Во время прогона раз в минуту смотри CPU генератора (`top -l 2 -n 0 | grep "CPU usage"`). CPU > 80% — результаты недостоверны: остановить, перейти в облако, отметить в отчёте.
- **Grafana Cloud k6** (`k6 cloud run`): больше ~150 VU, stress выше этого, soak дольше 30 мин. Нет входа (команда вернёт ошибку авторизации) → попроси пользователя выполнить `k6 cloud login --token <токен>` самому; локальные этапы делай пока без облака.
- Расход: VUh ≈ VU × часы. Бесплатный лимит — по данным аккаунта (ориентир ~500 VUh/мес); не помещается — урезать soak/stress и сказать в плане.
- Переменные `-e` уходят в облако — только тестовые аккаунты staging.

Прогон (длинные — в фоне через `run_in_background`):
```bash
RUN=".qa/load/runs/$(date +%Y-%m-%d-%H%M)-load"; mkdir -p "$RUN"
set -a; . .qa/accounts.env; set +a          # тестовые аккаунты → __ENV
k6 run -e STAGE=load -e TARGET_VUS=<T> -e BASE_URL="<staging>" \
  --summary-export "$RUN/summary.json" --out csv="$RUN/timeline.csv.gz" \
  .qa/load/scripts/scenario.js 2>&1 | tee "$RUN/log.txt"
```
Облако — то же, но `k6 cloud run --include-system-env-vars -e STAGE=… -e TARGET_VUS=… -e BASE_URL=… .qa/load/scripts/scenario.js` (так аккаунты из `accounts.env` уходят в облако, не появляясь в команде); ссылку на прогон из лога — в `$RUN/cloud-url.txt`. Сводку облачного прогона бери из лога и интерфейса по ссылке; `--summary-export`/`--out csv` в облаке не пишутся — так и отметь для аналитика.

**`.qa/accounts.env` агент не открывает и не печатает** (правило проекта) — только `source` в той же команде, что и k6. Имена переменных — из `.qa/e2e/accounts.json` (`QA_USER_<ID>_EMAIL/PASSWORD`), `lib.js` → `accounts([...])`. Вход требует код из SMS/почты или капчу — логин под нагрузкой не делать: токены сессий из `.qa/auth/<роль>.json` достаёт отдельный маленький скрипт прямо в переменные окружения (без вывода на экран); если и так нельзя — сценарий только гостевой, в отчёте это отметить.
После каждого прогона: `ls "$RUN"` — файлы есть. После каждого этапа — автосохранение `.qa/handoff.md` (скилл `qa-handoff`): какой этап сделан, какой следующий.

## 7. Анализ и отчёт → агент `load-analyst`
Передай: plan.md, папки прогонов, `baseline.json` (если есть), map.md. Агент пишет `.qa/load/reports/YYYY-MM-DD.md`: вердикт по критериям, предел, узкое место с доказательствами, восстановление, сравнение с прошлым, находки и рекомендации; обновляет `baseline.json`, если load прошёл.

Покажи пользователю итог коротко: ✅/❌ по критериям, предел, 3–5 главных находок, путь к отчёту.

## 8. Находки → доска
Находки (сайт падает при N, p95 вне SLA, утечка, 5xx под нагрузкой) — в mifrat **только после «да»**, как новые задачи по правилам `qa-verdict` (язык проекта, цифры, этап и нагрузка, таблица из отчёта). Тикеты нагрузочными результатами не реджектить без явной связи.

## 9. Подготовка Mac (один раз, общее для всех проектов)
Проверь сам, пользователю покажи только недостающее:
- `k6 version` — нет: `brew install k6`.
- Grafana Cloud: аккаунт на grafana.com (бесплатно, регистрирует пользователь) → Testing & synthetics → Performance → Settings → токен → **пользователь** выполняет `k6 cloud login --token <токен>`.
- Proxyman: `ls /Applications/Proxyman.app` — нет: `brew install --cask proxyman` (ставит и `proxyman-cli` в `/usr/local/bin`; выгрузка: `proxyman-cli export-log -m domains -d <домен> -f har -o <файл>`). В Proxyman: **Certificate → Install Certificate on this Mac**, затем для устройства:
  - iPhone (та же Wi-Fi сеть): **Certificate → Install Certificate on iOS → Physical Devices** — прокси Mac в настройках Wi-Fi iPhone, установить профиль, Настройки → Основные → Об этом устройстве → Доверие сертификатам → включить;
  - симулятор iOS: **Install Certificate on iOS → Simulators**;
  - Android эмулятор: **Install Certificate on Android → Emulators** (через adb). Настоящий Android: приложения по умолчанию не доверяют пользовательским сертификатам — нужна debug-сборка (с `network_security_config`) от разработчиков или веб-версия;
  - SSL pinning — запросы не видны; попросить у разработчиков сборку для staging без pinning.
- Конвертер HAR → k6 (черновик): `npx --yes har-to-k6 <файл.har> -o <файл.js>` (через Node 22 — `with-node22`).

## 10. Повторный запуск
Если `.qa/load/` уже есть: разведку не повторять, если `map.md` моложе 30 дней и пользователь не сказал «заново» и не назвал новый раздел; план — показать прошлый с пометкой, что изменилось; после прогонов — сравнение с `baseline.json` обязательно.
