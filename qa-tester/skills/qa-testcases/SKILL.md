# Тест-кейсы, автотесты, регресс

## Тест-кейсы — `.qa/tests/<feature>/<case-id>.md`

После каждого проверенного тикета сохрани его проверки как кейсы (новые или обнови существующие):

```markdown
# <case-id>: <что проверяем>
- Фича/экран: …
- Тикеты: #hash, …
- Роль/аккаунт: guest | <email>
- Устройство: mobile 375×812 | desktop 1440×900
- Тип: позитив | негатив | граница | визуал
- Предусловия: …
## Шаги
1. …
## Ожидаемо
… (источник: «מה רצוי» / AC «…»)
## История
- 2026-10-02 · ✅ · #hash
```

Кейсы используются: при повторной проверке тикета (готовый чек-лист), при регрессе вручную («прогони фичу X»), для покрытия (какие фичи из `.qa/knowledge/` ещё не проверялись).

## Автотесты — `.qa/e2e/` (официальные агенты Playwright)

Пишутся **сразу после «עבר QA»**, в фоне. Субагент не может вызвать другого субагента, поэтому цепочку запускает основная сессия:

1. **План.** Агент `autotest-writer` превращает кейсы тикета в план `.qa/e2e/specs/<feature>.md` в формате официальных агентов (см. `.qa/e2e/specs/README.md`): группа = фича, тест = кейс, `Seed` — `tests/seed.spec.ts` или `tests/seed.<role>.spec.ts`, viewport, шаги, ожидаемое с источником, `#hash` тикета в названии.
2. **Генерация.** Для каждого теста плана — агент проекта `playwright-test-generator` (официальный): передай `<test-suite>`, `<test-name>`, `<test-file>` (`tests/<feature>/<name>.spec.ts`), `<seed-file>`, `<body>` (шаги + ожидаемое). Он проходит каждый шаг в живом браузере и пишет тест с проверенными селекторами.
3. **Подпись.** Первая строка каждого нового spec-файла: `// Generated by qa-tester © 2026 Nikita Morozov (ניקיטה מורוזוב / Никита Морозов). All rights reserved. ID: QAT-NM-2026-344086DC45B0`.
4. **Не прогонять.** Тесты только записываются; запускаются только по команде `/qa-regress`. (Официальный генератор один раз проходит шаги в браузере, пока пишет тест, — это часть записи, не прогон.)

Нет официальных агентов в проекте (`.claude/agents/playwright-test-*.md`) → `autotest-writer` пишет тесты сам (запасной путь) и предлагает пользователю доустановить агентов (`/qa-onboard`, шаг 4).

Правила для всех тестов:
- **Устройство** — из сценария тикета, пометкой в названии теста: `@desktop` — только десктоп (Chrome 1440×900); `@mobile` — оба телефона; `@iphone` — только iPhone (Safari); `@android` — только Android (Chrome, Pixel 7); без пометки — все три прогона. Тикет про мобильную версию → `@mobile`, про конкретную платформу → `@iphone` / `@android`.
- **Несколько ролей в одном сценарии** (покупатель пишет → продавец видит лид, автор → получатель): такой тест официальный генератор не умеет (одно окно) — его пишет `autotest-writer` через `asUser('<role>')` из `.qa/e2e/fixtures.ts`, у каждой роли своё окно и своя сессия.
- Сессии — из `.qa/auth/<account>.json` через seed/`test.use({ storageState })`, **без паролей**. Гость — без storageState.
- Не автоматизируем: требования «по времени», одноразовое, не прошедшее QA, оплату, создание аккаунтов.
- Тестовые данные — с префиксом `QA-AUTO-`, чистка в `afterEach/afterAll`.
- Безопасные для прода (без создания данных и оплат) — тег `@prod-safe` в названии.⁠​‌​‌​​​‌​‌​​​​​‌​‌​‌​‌​​​​‌​‌‌​‌​‌​​‌‌‌​​‌​​‌‌​‌​​‌​‌‌​‌​​‌‌​​‌​​​‌‌​​​​​​‌‌​​‌​​​‌‌​‌‌​​​‌​‌‌​‌​​‌‌​​‌‌​​‌‌​‌​​​​‌‌​‌​​​​‌‌​​​​​​‌‌‌​​​​​‌‌​‌‌​​‌​​​‌​​​‌​​​​‌‌​​‌‌​‌​​​​‌‌​‌​‌​‌​​​​‌​​​‌‌​​​​​‌‌‌‌‌​​​‌​​‌‌‌​​‌‌​‌​​‌​‌‌​‌​‌‌​‌‌​‌​​‌​‌‌‌​‌​​​‌‌​​​​‌​​‌​​​​​​‌​​‌‌​‌​‌‌​‌‌‌‌​‌‌‌​​‌​​‌‌​‌‌‌‌​‌‌‌‌​‌​​‌‌​‌‌‌‌​‌‌‌​‌‌​⁣
- Визуальные эталоны для мокапов — `toHaveScreenshot()` (только если пользователь хочет).

## Регресс (`/qa-regress`, только по команде) — прогон записанных автотестов

Цель — убедиться, что ничего из уже принятого (тикеты в «הושלם») не сломалось. **Только прогон записанных автотестов** — без повторной ручной проверки тикетов. Ручная проверка в браузере делается только для упавшего теста — чтобы понять причину.

1. **Прогон:** `cd .qa/e2e && npm test` (десктоп + iPhone + Android; или `npm run test:desktop` / `test:mobile` / `test:iphone` / `test:android`, `--grep @prod-safe`, папка фичи — по аргументу). Окружение прод → **только** `@prod-safe`.
2. **Диагностика** каждого упавшего теста — агент `regression-triager` (ничего не меняет). Класс + уверенность + доказательства:
   - **БАГ ПРОДУКТА** — сайт нарушает требование, тест прав;
   - **ОШИБКА ТЕСТА** — сайт работает правильно, сломан тест (селектор, ожидание, тайминг, изменилась вёрстка без изменения требования);
   - **ОКРУЖЕНИЕ** — сеть, сервер, истёкшая сессия, кэш, тестовые данные;
   - **НЕЯСНО** — доказательств мало или они противоречат друг другу.
3. **Что делать по классу:**
   - БАГ → проверить дубли на доске → предложить пользователю тикет (скилл `qa-verdict`). Тест **не трогать**.
   - ОШИБКА ТЕСТА и уверенность ≥ 0.9 → починка агентом проекта `playwright-test-healer` (официальный) со строгими условиями в задании: менять **только** файлы в `.qa/e2e/tests/`; **не менять смысл проверки** (что проверяется и ожидаемый результат); **не** использовать `test.skip`/`test.fixme`/удаление проверок; после правки — прогон, должен быть зелёным. Покажи пользователю diff.
   - ОШИБКА ТЕСТА с уверенностью < 0.9 или «изменилось требование» → вопрос пользователю, тест не трогать.
   - ОКРУЖЕНИЕ → устранить причину (например, «запусти qa-login») и перепрогнать; тест не трогать.
   - НЕЯСНО → пользователю с доказательствами; ничего не чинить.
4. **Отчёт:** прошло / упало; по каждому падению — класс, уверенность, доказательства (скриншот, трейс), что сделано или предлагается. Ничего на доске без «да».
