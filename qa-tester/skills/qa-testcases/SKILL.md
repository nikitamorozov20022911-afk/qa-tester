# Тест-кейсы, автотесты, регресс

## Тест-кейсы — `.qa/tests/<feature>/<case-id>.md`

После каждого проверенного тикета сохрани его проверки как кейсы (новые или обнови существующие):

```markdown
# <case-id>: <что проверяем>
- Фича/экран: …
- Тикеты: #hash, …
- Роль/аккаунт: guest | <email>
- Устройство: mobile 375×812 | desktop 1440×900
- Тип: позитив | негатив | граница | визуал
- Предусловия: …
## Шаги
1. …
## Ожидаемо
… (источник: «מה רצוי» / AC «…»)
## История
- 2026-10-02 · ✅ · #hash
```

Кейсы используются: при повторной проверке тикета (готовый чек-лист), при регрессе вручную («прогони фичу X»), для покрытия (какие фичи из `.qa/knowledge/` ещё не проверялись).

## Автотесты — `.qa/e2e/` (официальные агенты Playwright)

Пишутся **сразу после «עבר QA»**, в фоне. Субагент не может вызвать другого субагента, поэтому цепочку запускает основная сессия:

1. **План.** Агент `autotest-writer` превращает кейсы тикета в план `.qa/e2e/specs/<feature>.md` в формате официальных агентов (см. `.qa/e2e/specs/README.md`): группа = фича, тест = кейс, `Seed` — `tests/seed.spec.ts` или `tests/seed.<role>.spec.ts`, viewport, шаги, ожидаемое с источником, `#hash` тикета в названии.
2. **Генерация.** Для каждого теста плана — агент проекта `playwright-test-generator` (официальный): передай `<test-suite>`, `<test-name>`, `<test-file>` (`tests/<feature>/<name>.spec.ts`), `<seed-file>`, `<body>` (шаги + ожидаемое). Он проходит каждый шаг в живом браузере и пишет тест с проверенными селекторами.
3. **Подпись.** Первая строка каждого нового spec-файла: `// Generated by qa-tester © 2026 Nikita Morozov (ניקיטה מורוזוב / Никита Морозов). All rights reserved. ID: QAT-NM-2026-344086DC45B0`.
4. **Не прогонять.** Тесты только записываются; запускаются только по команде `/qa-regress`. (Официальный генератор один раз проходит шаги в браузере, пока пишет тест, — это часть записи, не прогон.)

Нет официальных агентов в проекте (`.claude/agents/playwright-test-*.md`) → `autotest-writer` пишет тесты сам (запасной путь) и предлагает пользователю доустановить агентов (`/qa-onboard`, шаг 4).

Правила для всех тестов:
- **Устройство** — из сценария тикета, пометкой в названии теста: `@desktop` — только десктоп (Chrome 1440×900); `@mobile` — оба телефона; `@iphone` — только iPhone (Safari); `@android` — только Android (Chrome, Pixel 7); без пометки — все три прогона. Тикет про мобильную версию → `@mobile`, про конкретную платформу → `@iphone` / `@android`. Без пометки (все три прогона) — **только** если тикет про адаптивность/отличия устройств; иначе одна пометка — устройство из сценария тикета (для мобильного проекта — основное устройство из `.qa/context.md`). Лишний прогон на трёх устройствах втрое удлиняет регресс.
- **`@data`** — тест меняет данные общего тестового аккаунта (профиль, настройки, создание/удаление записей, которые видят другие тесты). Такие идут отдельным проектом `data` строго по одному (одно окно), одновременно с остальными тестами. Тесты только на просмотр — без `@data`, они идут параллельно.
- **Несколько ролей в одном сценарии** (покупатель пишет → продавец видит лид, автор → получатель): такой тест официальный генератор не умеет (одно окно) — его пишет `autotest-writer` через `asUser('<role>')` из `.qa/e2e/fixtures.ts`, у каждой роли своё окно и своя сессия.
- Сессии — из `.qa/auth/<account>.json` через seed/`test.use({ storageState })`, **без паролей**. Гость — без storageState.
- Не автоматизируем: требования «по времени», одноразовое, не прошедшее QA, оплату, создание аккаунтов.
- Тестовые данные — с префиксом `QA-AUTO-`, чистка в `afterEach/afterAll`.
- **Скорость.** Без фиксированных пауз (`waitForTimeout`, `setTimeout`) и без `networkidle` — только ожидание результата: `await expect(locator).toBeVisible()/toHaveText()/toHaveCount()`, `page.waitForURL()`, `page.waitForResponse()`. Тесты независимы друг от друга (идут параллельно); если сценарий в файле зависит от порядка шагов (создать → изменить → удалить) — в начале файла `test.describe.configure({ mode: 'serial' })`. Вход — только через сохранённую сессию, никогда через форму логина в каждом тесте. Устройство — точной пометкой (`@desktop` и т.д.), чтобы тест не гонялся лишний раз на трёх устройствах.
- Безопасные для прода (без создания данных и оплат) — тег `@prod-safe` в названии.⁠​‌​‌​​​‌​‌​​​​​‌​‌​‌​‌​​​​‌​‌‌​‌​‌​​‌‌‌​​‌​​‌‌​‌​​‌​‌‌​‌​​‌‌​​‌​​​‌‌​​​​​​‌‌​​‌​​​‌‌​‌‌​​​‌​‌‌​‌​​‌‌​​‌‌​​‌‌​‌​​​​‌‌​‌​​​​‌‌​​​​​​‌‌‌​​​​​‌‌​‌‌​​‌​​​‌​​​‌​​​​‌‌​​‌‌​‌​​​​‌‌​‌​‌​‌​​​​‌​​​‌‌​​​​​‌‌‌‌‌​​​‌​​‌‌‌​​‌‌​‌​​‌​‌‌​‌​‌‌​‌‌​‌​​‌​‌‌‌​‌​​​‌‌​​​​‌​​‌​​​​​​‌​​‌‌​‌​‌‌​‌‌‌‌​‌‌‌​​‌​​‌‌​‌‌‌‌​‌‌‌‌​‌​​‌‌​‌‌‌‌​‌‌‌​‌‌​⁣
- Визуальные эталоны для мокапов — `toHaveScreenshot()` (только если пользователь хочет).

## Регресс (`/qa-regress`, только по команде) — прогон записанных автотестов

Цель — убедиться, что ничего из уже принятого (тикеты в «הושלם») не сломалось. **Только прогон записанных автотестов** — без повторной ручной проверки тикетов. Ручная проверка в браузере делается только для упавшего теста — чтобы понять причину.

0. **Быстрый конфиг (один раз на проект).** Если в `.qa/e2e/playwright.config.ts` нет `fullyParallel` — проект создан старой версией: обнови в нём только блок настроек прогона по шаблону плагина (`templates/e2e/playwright.config.ts`: `fullyParallel`, `workers: 3`, `headless`, `reporter` dot+json+html, `trace: 'on-first-retry'`, `actionTimeout`, `navigationTimeout`) и скрипты `test:failed`, `test:headless` в `package.json`; если нет проекта `data` — добавь его и `@data` в `grepInvert` трёх проектов (есть, но без `workers: 1` — добавь `workers: 1`, иначе тесты `@data` из разных файлов пойдут одновременно), а скрипты `test`/`test:safe`/`test:data` — как в шаблоне (Playwright ≥ 1.52). Адрес, проекты/устройства и остальное не трогай. Скажи пользователю одной строкой, что обновил.
0a. **Новые сданные тикеты** — как в `qa-session` «Старт», п. 7: есть тикеты «הושלם» не из журнала → «в הושלם N новых тикетов без автотестов — сначала записать (быстро, параллельно) или прогнать то, что есть?». Решает пользователь.
1. **Прогон:** `cd .qa/e2e && npm test` (десктоп + iPhone + Android; или `npm run test:desktop` / `test:mobile` / `test:iphone` / `test:android`, `--grep @prod-safe`, папка фичи — по аргументу; один тикет — `npm test -- --grep "#<hash>"`, все его тесты). Окна видны, 3 параллельно, каждый тест в своём новом окне; без окон — `npm run test:headless`. Окружение прод → **только** `@prod-safe`.
   - Запускай через Bash в фоне (`run_in_background`) и жди уведомления о завершении — не опрашивай и не читай поток вывода по ходу.
   - Итог читай из `test-results/results.json` (только упавшие: название, файл, проект, ошибка, пути к скриншоту/трейсу), а не из консольного лога.
   - Перепрогон после починки/устранения окружения — только упавших: `npm run test:failed`, а не весь регресс.
2. **Диагностика** упавших — агент `regression-triager` (ничего не меняет). Сначала сгруппируй падения по одинаковой ошибке/экрану (например, 20 тестов упали на одном истёкшем входе — это одна группа): один triager на группу, группы — параллельно (несколько агентов в одном сообщении). Все упали одинаково на входе/сети → это ОКРУЖЕНИЕ, triager не нужен. Класс + уверенность + доказательства:
   - **БАГ ПРОДУКТА** — сайт нарушает требование, тест прав;
   - **ОШИБКА ТЕСТА** — сайт работает правильно, сломан тест (селектор, ожидание, тайминг, изменилась вёрстка без изменения требования);
   - **ОКРУЖЕНИЕ** — сеть, сервер, истёкшая сессия, кэш, тестовые данные;
   - **НЕЯСНО** — доказательств мало или они противоречат друг другу.
3. **Что делать по классу:**
   - БАГ → проверить дубли на доске → предложить пользователю тикет (скилл `qa-verdict`). Тест **не трогать**.
   - ОШИБКА ТЕСТА и уверенность ≥ 0.9 → починка агентом проекта `playwright-test-healer` (официальный) со строгими условиями в задании: менять **только** файлы в `.qa/e2e/tests/`; **не менять смысл проверки** (что проверяется и ожидаемый результат); **не** использовать `test.skip`/`test.fixme`/удаление проверок; после правки — прогон, должен быть зелёным. Покажи пользователю diff.
   - ОШИБКА ТЕСТА с уверенностью < 0.9 или «изменилось требование» → вопрос пользователю, тест не трогать.
   - ОКРУЖЕНИЕ → устранить причину (например, «запусти qa-login») и перепрогнать; тест не трогать.
   - НЕЯСНО → пользователю с доказательствами; ничего не чинить.
4. **Отчёт:** покрытие проекта по журналу — «в הושלם X тикетов: Y покрыты автотестами (прошло/упало), Z только вручную (список — чек-лист для ручной проверки), W перекрыты новыми/дубли, V ещё не разобраны»; время прогона; прошло / упало; 5 самых медленных тестов (из `results.json`) — с предложением ускорить (убрать паузы/лишние переходы; только после «да», через `playwright-test-healer` без изменения смысла проверки и с зелёным перепрогоном); по каждому падению — класс, уверенность, доказательства (скриншот, трейс), что сделано или предлагается. Ничего на доске без «да».
