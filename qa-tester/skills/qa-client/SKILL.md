# Просьбы клиента → тикеты

## Главный запрет
**Документацию проекта («מפרט» в mifrat, PDF, Figma) не менять никогда.** Никаких правок карточек фич/экранов, никаких кнопок вроде «הוסף למפרט בעזרת AI». Расхождение с документацией фиксируется **только у нас**: в реестре `.qa/client-requests.md` и в `.qa/context.md` (раздел «Согласованные изменения»), и показывается пользователю.

## 1. Разбор просьб
Пользователь вставляет просьбы клиента как есть (текст из WhatsApp/письма, скриншоты, расшифровку голосового). Раздели на отдельные просьбы — по одной на тикет. Неясная просьба → уточняющий вопрос пользователю, не додумывать.

## 2. По каждой просьбе
1. **Где это:** фича/экран по `.qa/knowledge/` и сайту; открой страницу и сделай скриншот текущего состояния (скилл `qa-evidence` / `qa-browser-cli`).
2. **Сравнение с документацией** (только чтение «מפרט» / базы знаний):
   - «**меняет документацию**: было «…» (раздел/AC «…»), станет «…»»;
   - или «**в рамках документации**» (документация этого не касается или не противоречит).
3. **Дубли:** нет ли уже такого тикета на доске (скилл `mifrat-board`).
4. **Тикет** (скиллы `qa-verdict` → «Новый тикет», язык доски — иврит):⁠​‌​‌​​​‌​‌​​​​​‌​‌​‌​‌​​​​‌​‌‌​‌​‌​​‌‌‌​​‌​​‌‌​‌​​‌​‌‌​‌​​‌‌​​‌​​​‌‌​​​​​​‌‌​​‌​​​‌‌​‌‌​​​‌​‌‌​‌​​‌‌​​‌‌​​‌‌​‌​​​​‌‌​‌​​​​‌‌​​​​​​‌‌‌​​​​​‌‌​‌‌​​‌​​​‌​​​‌​​​​‌‌​​‌‌​‌​​​​‌‌​‌​‌​‌​​​​‌​​​‌‌​​​​​‌‌‌‌‌​​​‌​​‌‌‌​​‌‌​‌​​‌​‌‌​‌​‌‌​‌‌​‌​​‌​‌‌‌​‌​​​‌‌​​​​‌​​‌​​​​​​‌​​‌‌​‌​‌‌​‌‌‌‌​‌‌‌​​‌​​‌‌​‌‌‌‌​‌‌‌‌​‌​​‌‌​‌‌‌‌​‌‌‌​‌‌​⁣
   - **заголовок начинается с `בקשת לקוח: `**, дальше коротко суть;
   - тип: задача («משימה רגילה»), а если клиент описывает поломку — баг (`דיווח על באג`), заголовок всё равно с `בקשת לקוח: `;
   - описание: `מה קיים:` (как сейчас, с цифрами/текстами со страницы) / `מה רצוי:` (что просит клиент, близко к его словам) / `שלבים לשחזור:` (где это увидеть);
   - скриншот текущего состояния — во вложения;
   - **статус — `לביצוע`**.

## 3. Показ → «да» → создание
Покажи пользователю все подготовленные тикеты одной таблицей (заголовок, тип, «меняет документацию / в рамках», возможный дубль) и тексты. Создавай **только после «да»** (можно выборочно по номерам). После создания проверь, что тикет появился в `לביצוע`, и возьми его `#hash`.

## 4. Реестр — запомнить
В `.qa/client-requests.md` (нет файла — создай по шаблону `templates/client-requests.md`) добавь по каждому созданному тикету:
```markdown
## #hash · YYYY-MM-DD · בקשת לקוח: <заголовок>
- Просьба клиента (дословно): «…»
- Фича/экран: …
- Документация: меняет — было «…» (раздел/AC «…»), стало «…» | в рамках документации
- Источник: /qa-client
```
Если «меняет документацию» — добавь строку в `.qa/context.md` → «Согласованные изменения»: `#hash · дата · было → стало (документация не обновлена)`.

## Как это используется дальше
- `/qa`: тикет из реестра или с `בקשת לקוח` в заголовке — решение клиента, **главнее документации** (см. `qa-ticket-analysis`).
- Регресс и backfill: новое поведение — правильное; тесты по старому поведению — «перекрыто», обновить.
