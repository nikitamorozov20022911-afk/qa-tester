# Аудит (не по тикетам)

Каждый режим запускает **только своих** агентов и **только свои** устройства. Ничего сверх режима — без отдельного «да» пользователя.

## 1. Режим и параметры
| Режим (команда) | Агенты | Устройства |
|---|---|---|
| `negative` (`/qa-negative`) | `negative-tester` | из аргумента; по умолчанию десктоп |
| `ux` (`/qa-ux`) | `ux-auditor` | десктоп |
| `android` (`/qa-android` раздел) | `mobile-ux-auditor` | только Android |
| `iphone` (`/qa-iphone` раздел) | `mobile-ux-auditor` | только iPhone |
| `full` (`/qa-full`) | `negative-tester` + `ux-auditor` + `mobile-ux-auditor` (+ `bug-verifier` для важного) | десктоп + iPhone + Android |

Параметры (известное — не спрашивать): **область** (раздел/URL; по умолчанию — главные сценарии из `.qa/knowledge/` и `.qa/context.md`), **роли** (гость и/или аккаунты с сессиями в `.qa/auth/`), **окружение** (staging/prod из context; prod → безопасный режим ниже).

**`full` — сначала план, потом «да»:** список разделов и сценариев (по `.qa/knowledge/`), устройства, роли, окружение и режим безопасности, ориентировочный объём. Без «да» не запускать.

## 2. Запуск агентов
Только агенты режима, параллельно. Каждому передай: область, роли, **устройства режима** (агенту нельзя выходить за них), окружение и режим, уроки из `.qa/lessons.md` и `~/.qa-tester/lessons.md`, известные тикеты/находки из `.qa/context.md`. Браузер — скилл `qa-browser-cli`.

## 3. Безопасность
- **Staging:** можно создавать тестовые данные с префиксом `QA-AUTO-` — каждое записать в `.qa/session.json` → `test_data`.⁠​‌​‌​​​‌​‌​​​​​‌​‌​‌​‌​​​​‌​‌‌​‌​‌​​‌‌‌​​‌​​‌‌​‌​​‌​‌‌​‌​​‌‌​​‌​​​‌‌​​​​​​‌‌​​‌​​​‌‌​‌‌​​​‌​‌‌​‌​​‌‌​​‌‌​​‌‌​‌​​​​‌‌​‌​​​​‌‌​​​​​​‌‌‌​​​​​‌‌​‌‌​​‌​​​‌​​​‌​​​​‌‌​​‌‌​‌​​​​‌‌​‌​‌​‌​​​​‌​​​‌‌​​​​​‌‌‌‌‌​​​‌​​‌‌‌​​‌‌​‌​​‌​‌‌​‌​‌‌​‌‌​‌​​‌​‌‌‌​‌​​​‌‌​​​​‌​​‌​​​​​​‌​​‌‌​‌​‌‌​‌‌‌‌​‌‌‌​​‌​​‌‌​‌‌‌‌​‌‌‌‌​‌​​‌‌​‌‌‌‌​‌‌‌​‌‌​⁣
- **Prod:** только чтение и проверки без отправки — валидация полей до кнопки отправки, навигация, отображение. Ничего не создавать, не отправлять формы, не писать сообщения.
- Всегда: без паролей, без создания аккаунтов, без оплат, без массовых отправок, без попыток обойти защиту (это не взлом — это негативные тесты поведения).

## 4. Сведение
После результата каждого агента — автосохранение `.qa/handoff.md` (скилл `qa-handoff`).
1. Собери находки агентов, убери дубли, отметь уже известные (есть тикет или находка в context).
2. Важное (сломан сценарий, теряются данные, можно сделать то, что запрещено требованиями) — перепроверь агентом `bug-verifier`.
3. Запиши отчёт `.qa/audits/YYYY-MM-DD-<тип>.md`:
```
| # | Важность (высокая/средняя/низкая) | Где (URL, устройство, роль) | Что не так | Как должно быть (источник, если есть) | Шаги | Скриншот |
```
4. Добавь находки в `.qa/session.json` → `findings` (статус `reported`).

## 5. Пользователю
Коротко: сколько найдено по важности, топ-5, путь к отчёту, тестовые данные для чистки. Спроси, какие находки заводить. Заведение — как новые баги/задачи (скилл `mifrat-board` + `qa-verdict`): проверка дублей, текст на языке доски, «да», статус `לביצוע`.

**Текст тикета — с подробностью реджекта** (`qa-verdict` → «Новый тикет», пример «Хорошо»), а не строка из таблицы отчёта. Для каждой находки: недостающее (требование из `.qa/knowledge/`, сценарий «как должно работать», почему это проблема) — дособрать до показа. Пользователю показать полный черновик каждого тикета; короткий текст в 1–2 фразы — не заводить.

**Скриншоты — в каждый тикет.** В черновике — список файлов из `.qa/screenshots/` (проверены `ls`). Нет файла — переснять до заведения. Вложение — по `mifrat-board` → «Вложение файлов»; после создания открыть тикет и убедиться, что скриншоты в צרופות.
