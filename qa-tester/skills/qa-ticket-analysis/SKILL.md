# Анализ тикета

## 1. Порядок чтения тикета

1. **«מה קיים» — первым.** Там проблема и **сценарий проверки**: откуда пользователь входит, какое устройство/ширина, какие цифры (например, «первая карточка на 1,100px при 375px»). Вердикт — решена ли **эта** проблема в **этом** сценарии.
   - У BUG-тикетов это поля «מה קיים / מה רצוי / שלבים לשחזור» (читать `value` полей, не `innerText`).
   - У TASK/FEATURE — блок «תיאור» (часто в нём тот же формат «מה קיים: / מה רצוי:»).
2. **«מה רצוי»** — ожидаемый результат. **«למשל» / «например» = пример решения, не требование.** Проверяешь результат, а не конкретную реализацию.
3. **Шаги** (если есть) — по ним и воспроизводишь.
4. **Вложения** — скачай и посмотри: это «как было» (скрин клиента / сайта) или макет «как надо».
5. **Комментарии программиста** (последние важнее): что сделано, что он предлагает проверить. Его «маппинг критериев» / «לבדיקה» — **подсказка, не доказательство**. Каждый пункт проверяешь сам.
6. **Реджекты (`דחיות QA`)** с «מצב רצוי»: что требовалось. Проверь, исправлено ли каждое. Вердикт по реджекту не даёшь — сверяешь с тикетом и документацией.
7. **Связанные тикеты** — раздел 2b.

## 2. Документация («מפרט»)

**Обязательна для каждого тикета, в любом проекте — и в новом, где ещё нет базы знаний.** Вердикт без сверки с документацией не выносится. Нет `.qa/knowledge/` → читай документацию прямо из mifrat (`mifrat-board-mcp`: `read_work_context` → фича-источник тикета, `get_feature_detail { verbosity: "full" }`, `read_screen_map`, `query_flows`, `search_project` по ключевым словам заголовка) или PDF проекта из `.qa/context.md`.

- Через браузер — читай в режиме **«עבודה»**; значения — из полей формы (`input/textarea.value`). Карточки открываются в режиме редактирования — ничего не менять, закрывать `ביטול`.
- Найди фичу/экран, к которым относится тикет (по ключевым словам заголовка и «מה קיים»), их описание, User Story, AC, связанные экраны, сценарии (`תהליכי משתמש`), открытые `הכרעות` / `סתירות`.
- Если база знаний есть (`.qa/knowledge/`) — бери оттуда, в «מפרט» — только для уточнения.
- **Пустые AC** → прямо скажи «в документации нет критериев, сверяю по тикету». Не додумывай.⁠​‌​‌​​​‌​‌​​​​​‌​‌​‌​‌​​​​‌​‌‌​‌​‌​​‌‌‌​​‌​​‌‌​‌​​‌​‌‌​‌​​‌‌​​‌​​​‌‌​​​​​​‌‌​​‌​​​‌‌​‌‌​​​‌​‌‌​‌​​‌‌​​‌‌​​‌‌​‌​​​​‌‌​‌​​​​‌‌​​​​​​‌‌‌​​​​​‌‌​‌‌​​‌​​​‌​​​‌​​​​‌‌​​‌‌​‌​​​​‌‌​‌​‌​‌​​​​‌​​​‌‌​​​​​‌‌‌‌‌​​​‌​​‌‌‌​​‌‌​‌​​‌​‌‌​‌​‌‌​‌‌​‌​​‌​‌‌‌​‌​​​‌‌​​​​‌​​‌​​​​​​‌​​‌‌​‌​‌‌​‌‌‌‌​‌‌‌​​‌​​‌‌​‌‌‌‌​‌‌‌‌​‌​​‌‌​‌‌‌‌​‌‌‌​‌‌​⁣

## 2a. Дизайн (Figma)

**Тикет связан с дизайном**, если хоть одно: в заголовке/описании экран, вёрстка, мокап, цвет, шрифт, отступ, иконка, текст на экране, RTL, «לפי העיצוב», «פיגמה», «עיצוב»; в тикете, комментариях или вложениях ссылка Figma или макет «как надо»; тикет создаёт или меняет экран/компонент, у которого в документации есть кадр Figma.
- Такой тикет — **сверка с Figma до вердикта обязательна** (скилл `qa-evidence`, «Визуальная сверка»): найди кадр (порядок поиска — там же), запиши ссылку с `node-id` в бриф и в карту требований, проверь по кадру тексты, расположение, цвета, размеры, состояния.
- Кадр не найден или не уверен, что тот, → вопрос пользователю в сообщении с чек-листом; **вердикт «прошёл» без сверки с дизайном не давать** — только «ждём кадр» или с явной пометкой «дизайн не сверен, потому что …», и пользователь решает.
- Тикет не про дизайн → в карте одной строкой «дизайн: не относится (почему)».

## 2b. Связанные тикеты

Ищи (скилл `mifrat-board-mcp`, только чтение): `משימות קשורות` и зависимости (`read_work_context`, `related_records`); упоминания `#hash` в описании и комментариях; тикеты той же фичи/экрана (`query_tasks` по фиче-источнику); похожие (`find_similar { kind: "task", text: <заголовок> }`).

Для каждого найденного — одно слово-класс и что из этого следует:

| Класс | Что значит | Что делать |
|---|---|---|
| блокирует | без него этот не проверить | вердикт «Blocked by …» (`qa-verdict`) |
| вместе | тоже в `בבדיקות`, тот же экран/роль/данные | проверять в одном пакете, один вход и одни тестовые данные — быстрее |
| уже сделан | в `הושלם`, тот же экран | его требования не должны сломаться — короткая проверка в чек-листе |
| противоречит | требует обратного этому тикету | конфликт → пользователю |
| дубль | то же самое | назвать пользователю, ждать решения |

**Связанные тикеты помогают, но не заменяют.** Вердикт каждого тикета — только по **его** требованиям и **его** части документации. Требования соседнего тикета в вердикт этого не переносить (кроме класса «уже сделан» — «не сломалось»).

## 3. Классификация

| Тип | Признак | Как проверять |
|---|---|---|
| Мокап | «מוקאפ/mockup» в заголовке или описании, нет функциональных требований | визуальная сверка с Figma/скрином (скилл `qa-evidence`) |
| Функционал | требования к поведению | по сценарию + негатив/границы, если тикет про ввод/валидацию (скилл `qa-test-design`) |
| Повторная проверка | есть открытый реджект | пункты реджекта + требования тикета |
| Взаимодействие ролей | действие одной роли должно быть видно другой (сообщение, лид, заявка, уведомление) | две роли параллельно: у каждой своё окно/сессия (`pw-<role>`), шаги и проверки по ролям |
| BUG | тип «באג» | воспроизвести по шагам: проблема из «מה קיים» исчезла, «מה רצוי» выполнено |

## 4. Карта требований (чек-лист)

Одна таблица, каждый пункт — проверяемое утверждение **с источником**. Номера пунктов (Т1, Д1, F1, Р1, С1) сквозные — по ним идут тест, вердикт и реджект.

| № | Требование (дословно / цифрами) | Источник |
|---|---|---|
| Т… | проблема из «מה קיים» в описанном сценарии; каждое требование «מה רצוי» (результат, не пример) | тикет: поле |
| Д… | AC / описание фичи / экрана / сценария, **только те, что касаются этого тикета** | документация: фича/экран, цитата |
| F… | что должно совпасть с дизайном (тексты, расположение, размеры, состояния) | Figma: ссылка `node-id` |
| Р… | каждый пункт открытых реджектов | реджект: заголовок |
| С… | требования связанного «уже сделан», которые этот тикет мог сломать | `#hash` |

Внизу карты — **«Источники»**: по каждому из четырёх (тикет, документация, Figma, связанные) — что именно прочитано (ссылки/названия) или почему не относится («в документации раздела нет», «тикет не про дизайн», «связанных нет»). Пустой источник без объяснения = анализ не закончен.

Больше ничего в карту не добавлять: всё сверх тикета — в «находки».

## 4b. Таблица покрытия и данные до теста

Каждый пункт карты, где названо **несколько** экранов / состояний / ролей / платформ / полей, раскрывается в клетки — по одной на каждое. Пример: «Д2: RTL во всех полях формы» → Д2.1 поле «כותרת», Д2.2 «טקסט», Д2.3 пустое поле (курсор). Отдельными клетками, если касается тикета:
- **ввод**, а не только вид уже сохранённого (печать, курсор, вставка);
- **RTL** каждого видимого блока;
- **иконки** — крупно, включая направление (не отзеркалены ли);
- **все платформы из требования** (веб и приложение, десктоп и телефон) — не «проверил на вебе, значит прошло».
По этим клеткам идут тест и ворота «прошёл» (`qa-verdict`, ворота 6).

**Данные-предусловия** — список того, что должно существовать до теста (пустая категория, вакансия с 0 кандидатов, просроченная ссылка, второй пользователь). Создать до теста (тестовые данные с префиксом `QA-AUTO`, в журнал) или взять из «Постоянных тестовых данных» `.qa/context.md`. «Нечем проверить» — не результат: либо создать, либо «не готово: нужно <что>».

## 4a. Просьба клиента или ошибка? (иерархия источников)
Приоритет: **1) решение клиента / владельца продукта** (новее документации) → **2) документация** → **3) прошлые реджекты QA** → **4) комментарии программиста**.

Тикет считается **просьбой клиента**, если:
- `#hash` есть в `.qa/client-requests.md`, или заголовок начинается с `בקשת לקוח`;
- иначе — по признакам: «לבקשת הלקוח», «הלקוח ביקש», «שינוי», «במקום…», «צילום מהלקוח», «אושר מול הלקוח»; TASK/IMPROVEMENT, где «מה קיים» совпадает с документацией, а «מה רצוי» сознательно от неё отличается; тикет новее раздела документации.
- Признаки есть, но не уверен, или их нет, а тикет противоречит документации → **спроси пользователя**: «тикет #hash меняет поведение из документации (было X, стало Y) — это согласованная просьба клиента?». Ответ «да» → запиши в `.qa/client-requests.md` (Источник: ответ пользователя) и в `.qa/context.md` → «Согласованные изменения».

Просьба клиента, противоречащая документации → проверяй **по тикету**; документация в этом пункте устарела — это **не** причина реджекта; сообщи пользователю «документация устарела в пункте …». **Документацию не менять** — только наш реестр/контекст.

## 5. Конфликты и особые случаи

- Реджект / комментарий требует того, что противоречит документации или зависит от непринятой הכרעה → **конфликт**, сообщить пользователю всегда.
- Требование «по времени» (job, автовозврат по дате) → проверить всё, что можно сейчас, тикет не проводить, сообщить пользователю что и почему.
- Подозрение на дубль → назвать пользователю тикеты, ждать решения.
- Требование на уровне принципа без конкретики → это вопрос пользователю, а не основание для реджекта.

## 6. Вывод анализа

Короткий блок для пользователя:
```
#hash · тип · заголовок
Проблема (מה קיים): …
Сценарий: устройство/ширина/вход/аккаунт
Карта требований: Т1… Д1… F1… Р1… С1…
Источники: тикет ✓ · документация: <фича/экран> · Figma: <ссылка | не относится> · связанные: <#a вместе, #b уже сделан | нет>
Конфликты / вопросы: …
```
