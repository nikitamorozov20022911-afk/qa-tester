# QA-плагин для Claude Code — дизайн-документ

> Статус: черновик на согласование · обновлено 2026-10-02
> Ничего из этого ещё не собрано. Сборка начинается только после «ок».

---

## 1. Цель

Плагин `qa-tester`, который кладётся в папку любого тестируемого проекта и ведёт QA-процесс по тикетам в mifrat:
онбординг проекта → проверка тикетов из «בבדיקות» → действия на доске → новые баги → ежедневная сводка → тест-кейсы и автотесты → регресс по команде.

Пользователь в идеале только смотрит и подтверждает действия на доске.

---

## 2. Принципы

1. **Документация главнее прошлых реджектов.** Вердикт ставится по требованиям тикета + документации, а не по реджекту.
2. **Проверка полная, за один заход.** «Прошёл, но не всё проверено» не бывает.
3. **Генерация ≠ проверка.** Баг перед реджектом перепроверяет отдельный агент.
4. **Всё, что пишет на доску, — через подтверждение** (кроме режима «отправляй без подтверждения»).
5. **Состояние на диске, а не в голове агента:** журнал сессии обновляется после каждого тикета.
6. **Не уверен — спроси.** Трактовка ≠ требование документации.
7. **Начинать с «מה קיים».** Там описана проблема и сценарий проверки (откуда вход, устройство, цифры). Вердикт — решена ли эта проблема.
8. **«למשל» в «מה רצוי» — пример решения, не требование.** Проверяем результат, а не конкретную реализацию.
9. **Строго в объёме тикета.** Всё замеченное попутно — отдельный список находок для пользователя, не в вердикт.
10. **Свежая версия сайта.** Перед тестом убедиться, что страница не из кэша service worker (баннер «גרסה חדשה», `transferSize: 0`); при необходимости очистить SW и кэш — сценарий «новый пользователь».

> Уроки пробного прогона 2026-10-02 (biz4sale, `#6c3fdf78`): пункты 7–10 добавлены после того, как агент сначала проверял поиск и десктоп вне объёма тикета, не опираясь на «מה קיים».

## 3. Внешняя среда

### 3.1 mifrat
- Колонки: `רשימת משימות` (backlog) → `לביצוע` → `בביצוע` → `בבדיקות` → `הושלם`.
- Тестируем **только** `בבדיקות`.
- Типы карточек: FEATURE, TASK, IMPROVEMENT, BUG. Есть спринты.
- **ID тикета — `#226301e0` (hash).** «TC» на карточке — это наши тест-кейсы, не номер тикета.
- Бейдж «N ⊗» на карточке — число открытых реджектов.
- Документация: вкладка «מפרט» (фичи, экраны, персоны, הכרעות, סתירות) и/или PDF. Позже — через MCP (Base44).

### 3.2 Карточка тикета
- Кнопки: `דחה משימה`, `לא ניתן לשחזר`, `עבר QA`, `דחיות QA (N)`, `סמן כתקלת תפעול` (**не нажимать**), AI-кнопки (не используем).
- Сайдбар: עדיפות, קטגוריה, ספרינט, אחראי, הערכת שעות, **סטטוס**.
- Блоки: תיאור, User Story, קבצים מצורפים, משימות קשורות, הערות (комментарии программиста).
- Реджект внутри: статус `פתוח`, `מצב נוכחי`, `מצב רצוי`, שלבים, URL-суффикс, вложения, кнопка **`סמן כטופל`**.

### 3.3 Форма реджекта (`דחה משימה`)
`כותרת הדחייה*` · `התנהגות נוכחית*` · `התנהגות רצויה*` · `שלבים לשחזור` (каждый шаг — своё поле, «הוסף שלב») · `סופיקס URL` · `קישור לשחזור` · `קבצים מצורפים` · Allure (**не трогать**).

### 3.4 Новый тикет (`+` → `משימה חדשה`)
- **Не баг (task: дизайн, текст, RTL, UX, валидация):** тип «משימה רגילה». Заголовок + описание в формате:
  ```
  מה קיים:
  <текст>
  מה רצוי:
  <текст>
  שלבים לשחזור:
  1. ...
  ```
- **Баг:** кнопка `דיווח על באג` → поля `מה קרה בפועל?*`, `מה צריך לקרות?*`, `שלבים לשחזור` (+ `הוסף שלב`).
- Затем: тип / סטטוס / עדיפות / אחראי → «קבצים וקישורים» → צרופות (скриншоты) → `צור משימה` → проверить, что тикет появился.

### 3.5 Технические приёмы mifrat (UI)
- Карточку открывать кликом по заголовку `h4` через JS.
- Длинные колонки подгружаются при прокрутке — «не найден» ⇒ прокрутить вниз.
- Выпадающий список: элемент `[role=option]` с нужным текстом.
- Шаги склеиваются ⇒ заполнять через JS (native value setter + `input`), потом проверить каждое поле.
- **Выделение тикетов: Cmd+клик**, проверить счётчик «N נבחרו». Кнопку `מחק` не нажимать никогда.
- Карточки в «מפרט» открываются в режиме редактирования — ничего не менять, закрывать через `ביטול`.
- «מפרט» в режиме «ספר» раскрывает не все фичи — читать в режиме «עבודה», значения брать из полей формы (`input/textarea.value`), а не из `innerText`.
- Если у фичи пустые AC — прямо сказать «в документации нет критериев, сверяю по тикету», не додумывать.
- После `עבר QA` проверить, что тикет переехал в колонку `הושלם`.

## 4. Таблица вердиктов

| Ситуация | Действие |
|---|---|
| Всё по тикету + документации + открытым реджектам выполнено | На каждом открытом реджекте `סמן כטופל` → `עבר QA` |
| Найдены невыполненные требования (новые или частично исправленный реджект) | `דחה משימה` — **только по невыполненному** |
| Открытый реджект не исправлен **вообще** | Новый реджект не писать, сайдбар `סטטוס` → `לביצוע` |
| В реджекте просьба/вопрос тестера, программист не ответил в комментариях | Сайдбар `סטטוס` → `לביצוע` |
| Блокирует другой тикет | `לא ניתן לשחזר` с заметкой «Blocked by <тикет>…», тикет остаётся в `בבדיקות` |
| Нет ресурса для проверки (данные, доступ, карта) | `דחה משימה`, в רצוי: «Please provide … to continue testing» |
| Требование зависит от непринятой הכרעה / контента заказчика | Проверить промежуточное состояние, **предложить** пользователю `לא ניתן לשחזר` |
| Требование «по времени» (job, автовозврат по дате) | Проверить всё, что можно сейчас, **не проводить**, сообщить пользователю что и почему ⚠️ *см. открытый вопрос 1* |
| Подозрение на дубль | Сообщить пользователю названия тикетов, ждать решения |
| Конфликт реджекта/комментария с документацией | Сообщить пользователю всегда; в тексте реджекта — только «как должно быть по документации» |
| Отклоняем тикет со старой пометкой `לא ניתן לשחזר` | Снять пометку `מחק סימון` |

### Правила текста реджекта / бага
- Язык — **иврит** по умолчанию (настраивается в `context.md`).
- Нейтрально, от лица системы и пользователя, без «я/QA».
- Не упоминать прошлые реджекты.
- В «רצוי» всегда: (1) какое требование не выполнено — цитата с названием фичи/экрана; (2) как должно работать по документации — сценарий.
- Первый шаг — под каким аккаунтом (email) заходить. Номера в тексте шагов не писать.
- Скриншот обязателен, проблема обведена красным.
- Комментарий программиста с «маппингом критериев» — подсказка что проверить, не доказательство.

## 5. Процессы

### 5.1 `/qa-onboard` — новый проект (один раз)
1. Спросить: ссылка на сайт, ссылка на доску, языки и язык по умолчанию, PDF документации, Figma/дизайн.
2. Параллельно агенты-экстракторы по PDF / «מפרט»:
   фичи · экраны · роли (персоны) · сценарии и User Stories · הכרעות и סתירות.
3. `onboard-consolidator` сводит в связанную базу `knowledge/` (фича ↔ экраны ↔ роли ↔ AC).
4. `onboard-verifier` ищет дыры (экран упомянут, но не описан и т.п.).
5. Создать `context.md`, шаблон `accounts.env`, скрипт `qa-login`.
6. Пользователь заполняет `accounts.env` и запускает `qa-login` → сессии сохранены.

### 5.2 `/qa` — сессия тестирования
1. Если есть `handoff.md` — предложить продолжить с него.
2. Загрузить `context.md`, проверить живость сессий (иначе: «запусти qa-login»).
3. Очередь: тикеты из `בבדיקות`; порядок — сначала под текущей ролью.
4. **По каждому тикету:**
   1. `ticket-researcher` (наперёд, пока тестируется предыдущий): тикет, комментарии, реджекты, связанные тикеты, нужные куски `knowledge/`, дизайн.
   2. Классификация: **мокап** (слово «мокап» в заголовке/описании, нет функциональных требований) / **функционал** / **повторная проверка после реджекта**.
   3. Чек-лист: требования тикета + AC фичи/экранов + сценарии + пункты открытых реджектов + негативные/граничные тесты (`qa-test-design`).
   4. Сверка источников, список конфликтов.
   5. Тест (`qa-tester`): по каждому пункту, под каждой нужной ролью; мокап — сверка с Figma/скрином. Скрины с красной обводкой. Тестовые данные — в журнал.
   6. `bug-verifier` независимо перепроверяет каждую находку.
   7. Вердикт по таблице §4 → показать пользователю → действие на доске.
   8. Записать тест-кейсы в `tests/`; если «עבר QA» — `autotest-writer` пишет автотест.
   9. Обновить `session.json`.
5. Новые баги вне тикетов: проверить дубли на доске → оформить (§3.4) → подтверждение → создать.
6. Итог сессии: прошло / вернули / помечено / новые тикеты / не проверено и почему / тестовые данные для чистки.
7. **«בדיקה יומית»:** Cmd+клик по всем тронутым тикетам из `session.json` → проверить «N נבחרו» → `עוד` → `צור סיכום` → «בדיקה יומית» → `שלח ליצירת סיכום` → дождаться «סיכום משימות», не закрывать → сверить с журналом, сообщить число и разделы.
8. Обновить `context.md`.

### 5.3 Handoff
- «сделай хендофф» → `handoff.md`: проект, текущий тикет и шаг, что проверено по чек-листу, роль, найденное, что дальше, открытые вопросы.
- «продолжаем» → прочитать `handoff.md` + `session.json` + `context.md` и продолжить.
- `session.json` обновляется после каждого тикета автоматически — страховка от внезапного конца контекста.

### 5.4 `/qa-regress` — по команде
Прогон автотестов (все / по фиче) → упавшие перепроверяются вручную → классификация: баг / нестабильный тест / изменился дизайн → для багов проверка дублей и предложение тикетов, для дизайна — предложение обновить тест.

## 6. Логин и браузер

- **Браузер: Playwright MCP**, отдельно от Chrome пользователя. Один проект = одна сессия Claude = свой браузер → проекты параллельно не мешают друг другу.
- **Логин:** скрипт `qa-login` (Playwright) читает `.qa/accounts.env`, заходит под всеми аккаунтами, сохраняет сессии в `.qa/auth/<account>.json`.
  - Скрипт пишет агент, **запускает пользователь** (одна команда). Агент не вводит пароли и не читает `accounts.env`.
  - Сессия истекла → агент просит перезапустить `qa-login`.
  - Совет программистам: увеличить срок жизни сессии на staging.
- **Регистрация** (создание аккаунтов): агент проверяет до финальной кнопки (поля, валидация, негатив/границы); финальную отправку делает пользователь.
- Оплата — только до экрана оплаты, карты не вводятся.
- Тестируем там, где скажет пользователь (бывает и прод).

## 7. Тест-кейсы и автотесты

### 7.1 Тест-кейсы — `.qa/tests/<feature>/<case>.md`
id · фича/экран · тикеты (`#hash`) · роль · предусловия · шаги → ожидаемое (+ ссылка на AC) · тип (позитив / негатив / граница / визуал) · история (дата → результат → тикет).

### 7.2 Автотесты — `.qa/e2e/<feature>.spec.ts`
- Пишутся **сразу после «עבר QA»**, должны пройти зелёными.
- Используют сохранённые сессии (`.qa/auth/`), без паролей.
- Не автоматизируем: «по времени», одноразовое, ещё не прошедшее QA.
- Мокапы: визуальный эталон после «עבר QA» (по желанию).
- Тестовые данные с префиксом `QA-AUTO-`, чистка после прогона.
- На проде гоняются только тесты с тегом `@prod-safe`.

## 8. Структура плагина

```
qa-tester/
  .claude-plugin/plugin.json
  .mcp.json                    ← Playwright MCP
  commands/
    qa-onboard.md
    qa.md
    qa-regress.md
  skills/
    qa-orchestrator/           ← цикл сессии, очередь, кого звать
    qa-context/                ← формат context.md, обновление
    qa-handoff/                ← «сделай хендофф» / «продолжаем»
    qa-checklist/              ← сведение источников, конфликты
    qa-test-design/            ← негатив, границы, классы эквивалентности
    qa-visual/                 ← сверка с Figma, скрины с обводкой
    qa-verdict/                ← таблица §4, правила текста
    mifrat-board/              ← все действия на доске + §3.5
    qa-testcases/              ← формат тест-кейсов
    qa-report/                 ← итог, чистка, «בדיקה יומית»
  agents/
    onboard-extractor.md       ← параметр: features|screens|roles|flows|decisions
    onboard-consolidator.md
    onboard-verifier.md
    ticket-researcher.md
    qa-tester.md
    bug-verifier.md
    autotest-writer.md
    regression-triager.md
  templates/
    context.md · handoff.md · session.json · accounts.env.example
    qa-login.ts · playwright.config.ts
```

### Данные в папке проекта
```
<проект>/.qa/
  context.md        ссылки, языки, аккаунты (без паролей), правила проекта, известные тикеты
  accounts.env      логины/пароли (заполняет пользователь, в .gitignore)
  auth/             сохранённые сессии
  knowledge/        фичи, экраны, роли, сценарии, הכרעות
  handoff.md
  session.json      журнал: тикеты, действия, тестовые данные, скриншоты
  screenshots/
  tests/            тест-кейсы
  e2e/              автотесты
```

## 9. Порядок сборки

1. **Пробный прогон без плагина** — один реальный тикет вручную по этому документу, чтобы проверить процесс и найти дыры.
2. Каркас плагина + `context`, `handoff`, `mifrat-board`, `qa-verdict`.
3. Playwright MCP + `qa-login` + проверка ролей (несколько сессий одновременно — проверить технически).
4. Цикл `/qa` с `ticket-researcher`, `qa-tester`, `bug-verifier`.
5. `/qa-onboard` с агентами-экстракторами.
6. Тест-кейсы + `autotest-writer`.
7. `/qa-regress`.
8. Прогон на реальном проекте, правки.
